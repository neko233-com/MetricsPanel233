# Repository Guide for Coding Agents

## Purpose

MetricsPanel233 is a high-performance, single-node Prometheus-ecosystem dashboard and metric-storage service with first-party UI, Go backend and JSON-first CLI. The product replaces selected Grafana dashboard and Prometheus-compatible storage workflows; it does not target full Grafana parity or distributed monitoring. See docs/project-goals.md for the source of truth.

## Source map

| Area | Owns |
| --- | --- |
| **cmd/metricspanel** | CLI entry point, server composition, command and HTTP integration |
| **internal/server** | HTTP routes and request-level API behavior |
| **internal/store** | Durable control-plane and metric storage operations |
| **internal/collector** | Scrape scheduling and supported direct/exporter collection |
| **internal/querycontext**, **internal/promcompat**, **internal/expressions**, **internal/sqlframes** | Query context, Prometheus compatibility, expressions and SQL result frames |
| **internal/grafana**, **internal/plugins** | Grafana resource compatibility and plugin lifecycle |
| **web/src** | React UI; features/ owns product pages and grafana/ owns compatibility/runtime integration |
| **tests/integration** | Docker-backed integration coverage |
| **docs** | Product contracts, compatibility status and development documentation |

Read the narrowest relevant source and contract first. A feature's server handler, storage implementation, UI consumer and schema examples may define separate parts of the behavior.

## Working rules

- Keep changes scoped and preserve unrelated user changes.
- Treat source, executable tests and current runtime behavior as authoritative. Update documentation when public behavior or a compatibility claim changes.
- Product UI uses the first-party primitives in `web/src/ui` and renderers in `web/src/render`. Do not add `@grafana/ui` imports to product features or pages. Grafana packages belong only to the optional import/plugin compatibility layer under `web/src/grafana` and must not be expanded.
- OTLP/HTTP metrics are received at `POST /v1/metrics` (alias `/otlp/v1/metrics`) and share the metric store and ingest role policy with Prometheus/MySQL/Redis collection.
- Grafana 13.2.3 documents selected interoperability behavior only. Do not treat the full Grafana parity inventory as the product roadmap.
- Keep credentials out of source, fixtures, logs, documentation and command output. Preserve the encryption and masking behavior for connection secrets.
- `--auth=token` is the compatibility default; `--auth=local` adds users, sessions and roles through `internal/localauth`. Passwords and session tokens must never be logged. The one-time setup token is printed to stdout only while no account exists.
- When adding a route, update the Admin/Editor/Viewer matrix in `internal/localauth/policy.go`; unknown mutations fail closed to Admin. Identity data lives in a separate SQLite catalog and is backed up with the control database and `secrets.key`.
- Public deployments bind loopback behind an HTTPS proxy, set `--root-url` to the real https origin, and list only the proxy CIDRs in `METRICSPANEL_TRUSTED_PROXIES`. Never publish port 7333 directly. `/api/health` is intentionally public and minimal; keep other health/metric routes authenticated.
- Do not hand-edit build output. The React bundle in web/dist is generated by Vite and embedded only for Go builds using the webui tag.
- Avoid unrelated database migrations, protocol changes or compatibility expansion when implementing a local fix.

## Fast development and verification

From web, run npm ci once and then npm run dev:workspace. It starts the Go API and Vite UI together; Vite provides frontend HMR and Ctrl+C stops both processes. See the [development guide](docs/development.md).

Run the narrowest relevant Go or frontend check first. For broad changes, use the same checks as [GitHub Actions](.github/workflows/ci.yml), including Docker integration only when the change needs that coverage. Do not infer browser, Docker or production acceptance from a source-level check.

## Contract documentation

docs/architecture.md maps runtime boundaries and docs/project-goals.md defines product scope. The design and HTTP contract documents under docs explain narrower behaviors and must state their scope and known limitations. Prefer one focused contract page per substantial subsystem over duplicating implementation details across the README.
