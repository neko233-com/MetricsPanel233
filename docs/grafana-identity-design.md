# Organization and identity design

Status: design only, reviewed against Grafana 13.2.3 OSS on 2026-10-12. No account, organization, team, session, service-account or ACL implementation is established by this document. Enterprise datasource permissions and custom RBAC roles are outside the requested OSS scope. The proposed implementation below is an engineering recommendation, not a claim that it already matches Grafana.

## Verified behavior and current boundaries

Grafana separates instance administrators from organization roles. Organization roles include Viewer, Editor, Admin and None; teams and resource permissions add organization-local grants. Viewer can query organization datasources, while the default Explore UI requires Editor or Admin. Therefore a private dashboard does not by itself make its underlying datasource private in OSS. [Pinned role documentation](https://github.com/grafana/grafana/blob/v13.2.3/docs/sources/administration/roles-and-permissions/_index.md), [OSS datasource permission registration](https://github.com/grafana/grafana/blob/v13.2.3/pkg/services/accesscontrol/ossaccesscontrol/datasource.go).

Grafana API authentication supports Basic authentication and service-account Bearer tokens. A service-account token belongs to one organization, inherits its account's permissions, and cannot perform instance administration. The pinned authentication code rejects expired/revoked tokens, a requested organization different from the token's organization, and legacy API keys without a service account. An `X-Grafana-Org-Id` header selects a context; it is not proof of membership. [HTTP authentication](https://github.com/grafana/grafana/blob/v13.2.3/docs/sources/developer-resources/api-reference/http-api/authentication.md), [service accounts](https://github.com/grafana/grafana/blob/v13.2.3/docs/sources/administration/service-accounts/_index.md), [token authentication source](https://github.com/grafana/grafana/blob/v13.2.3/pkg/services/authn/clients/api_key.go).

The current application has one Store, Collector, Alert engine, Prometheus API, plugin Manager, Live hub and SQL pool. `internal/server/server.go:85` checks an optional shared Bearer token and origin; it does not resolve a user or organization. `internal/model/plugin.go:64` rejects datasource `orgId` values other than 1. Plugin contexts in `internal/plugins/manager.go:333`, `internal/plugins/apps.go:24` and `internal/plugins/stream.go:14` identify every caller as organization 1 and an Admin named `metricspanel`. These are implementation gaps, rather than completed account support.

## Recommended isolation boundary

Introduce an instance service that authenticates requests, resolves a trusted principal and selects an organization server. Keep the existing configured SQLite database and ClickHouse database as organization 1. New organizations receive a separate SQLite database, its own `secrets.key`, and an organization-specific ClickHouse database when that backend is enabled. Do not copy organization 1's metrics, targets, credentials or dashboards when creating a new organization.

Each organization owns one Store, Collector, Alert engine, Prometheus API, Live hub, SQL pool and plugin Manager. This preserves existing transactions, UID relationships, optimistic revisions, dashboard history, notification outbox ordering and foreign keys within a single database. It avoids changing every legacy SQL statement to rely on an optional tenant filter. Organization selection must happen before entering these services, including background jobs and websocket connections.

The instance service owns identity storage, organization registration, the installed-plugin registry, package files and installation lifecycle. Organization servers must be created through one registry, not from request-supplied filesystem paths. Use a numeric organization ID to derive a validated directory and database identifier; validate resolved Windows paths remain inside the configured organization directory. Refuse unknown, disabled, deleting or uninitialized organizations.

The current `Server.Handler` should become an organization handler behind the instance dispatcher. Its origin checks and response headers remain useful, but its shared-token check must not independently bypass the new principal and route authorization. Instance routes, organization routes, public assets and deliberately public sharing endpoints need explicit classification; the current generic `/api` wrapper is insufficient.

The `app_settings` foreign key currently references the local `plugins` table. Moving the registry therefore requires an explicit app-settings migration: preserve all settings and secrets, replace that foreign key with instance-registry validation, and define package deletion/invalidation across organization servers. Merely pointing `Store.Plugin` at another database would leave a broken foreign key and inconsistent uninstall behavior. `internal/store/plugins.go:97`, `internal/store/apps.go:17`, `internal/plugins/manager.go:163` and `internal/server/apps.go:43` are the main change points.

Keep organization 1's physical paths and IDs stable. Use versioned, resumable startup migrations with maintenance gating before handlers/background workers start. Copy the installed registry into instance storage with a durable completion marker and inventory check. Cross-database startup steps require explicit recovery markers; do not claim a WAL transaction atomically commits several separate files. Organization creation and deletion similarly need `creating`, `active`, `deleting` and recovery states. Close workers, streams, SQL pools and plugin processes before removing an organization store.

## Credentials, datasource requests and plugin contexts

Current AES-GCM associated data is the datasource UID, `app:<pluginID>`, `target:<numericID>` or `contact-point:<UID>` (`internal/store/plugins.go:58`, `internal/store/apps.go:68`, `internal/store/resources.go:131`, `internal/store/notifications.go:79`). Preserve the original organization 1 key. Add an explicit ciphertext-version column/envelope and bind new encryption to a length-delimited tuple of version, organization ID, resource kind and immutable local identity. Separate organization keys and bound associated data prevent a copied ciphertext from resolving under another organization or resource kind.

Migrate existing ciphertext by decrypting with the original associated data and resealing with the new tuple inside that organization's migration transaction. Fail startup on a missing key or authentication error; never generate a replacement key for a populated store. Recognize legacy ciphertext only through its recorded version and the organization 1 migration path. A failed new-format decrypt must never fall back to legacy AAD. Test all four secret-bearing tables, including unchanged-password edits and application configuration.

Resolve datasource UIDs and numeric IDs from the selected organization Store before any query, health check, credential lookup, resource request or HTTP proxy. Apply one authorization predicate at the shared source-query boundary and at independent routes: `/api/ds/query`, chunked queries, datasource resources/proxy/health, native Prometheus endpoints, app resources and Live subscribe/publish. Include expression dependencies and server-side alert graph queries. Existing locations include `internal/server/plugins.go:218`, `internal/server/plugins.go:368`, `internal/server/plugins.go:427`, `internal/server/chunked.go:392`, `internal/server/expressions.go`, `internal/server/native_plugin_routes.go`, and `internal/server/plugin_prometheus.go`.

Datasource administration and app configuration require organization Admin. Datasource reads and queries follow OSS basic-role behavior; do not add an Enterprise datasource-permission editor as a substitute for missing organization isolation. HTTP proxy credentials come only from the selected Store. Strip or rebuild trusted organization/user headers from the principal; forwarding a browser's claimed organization is not authorization.

Per-organization plugin Managers may share verified package files while owning separate process/cache maps and Store references. Populate SDK `PluginContext.OrgID`, namespace and `backend.User` from the principal, including service-account identity and actual basic role. App/stream contexts need the same treatment as QueryData, health and resource calls. Namespace mapping must follow the instance's namespace policy, rather than another hardcoded `default`; Grafana's pinned namespace hook derives it from organization identity. [Namespace sync source](https://github.com/grafana/grafana/blob/v13.2.3/pkg/services/authn/authnimpl/sync/namespace.go).

`internal/alerting/engine.go:389` currently sends `X-Grafana-Org-Id: 1`. Organization workers need an internal principal explicitly bound to their organization and a narrow evaluation purpose. `internal/server/server.go:493` starts the existing background workers and self-ingestion; the instance service must own lifecycle and aggregate health without granting normal users instance-wide resource discovery. Per-organization SQL pools can retain their UID keys because their containing Server is isolated (`internal/server/sql_datasources.go:199`).

## Identity model and resource authorization

Proposed instance tables: users and password credentials; organizations and memberships; browser sessions; service accounts and token hashes; teams and team memberships; preferences and recovery/invite state; migration/lifecycle metadata. Every organization relationship includes a trusted organization ID. Human users may belong to several organizations. A service account belongs to exactly one organization. Server-admin status is distinct from an organization's Admin role.

Sessions use opaque random credentials stored as hashes, expiration/idle state and server-side revocation. Tokens are shown once and thereafter stored as hashes, with expiry, revoked state, account-disabled state and last-use metadata. Recheck membership/account state on authentication and revoke active requests/Live sessions on relevant changes. Basic authentication, browser login/logout, organization switching, user and team management, service-account/token APIs, and CLI credential selection must all use this same principal model. Existing token-free local mode, if retained, must be an explicit local-administration mode; it cannot silently grant anonymous Admin in multi-user mode.

Add organization-local resource permission tables for folders, dashboards and service-account management. Validate referenced user/team/service-account memberships against instance identity storage on write. Effective permissions combine applicable direct and inherited grants; resource Admin can manage permissions. Folder move, dashboard move and library references must resolve both ends in the same organization and check permissions on both source and destination. Cache keys include organization, principal/membership version, resource and permission version; changes invalidate cached grants.

Grafana's OSS dashboard permissions accept users, teams, built-in roles and service accounts, map View/Edit/Admin to explicit action sets, and resolve containing/ancestor folder scopes. Folder permissions also cover relevant alerts, silences and library panels. Service-account management has separate user/team Edit/Admin grants; management permission does not make the service account a team member. [Dashboard permission source](https://github.com/grafana/grafana/blob/v13.2.3/pkg/services/accesscontrol/ossaccesscontrol/dashboard.go), [folder permission source](https://github.com/grafana/grafana/blob/v13.2.3/pkg/services/accesscontrol/ossaccesscontrol/folder.go), [service-account permission source](https://github.com/grafana/grafana/blob/v13.2.3/pkg/services/accesscontrol/ossaccesscontrol/service_account.go).

Seed legacy organization 1 with equivalent access for its migration/bootstrap administrator. New root resources receive the appropriate defaults and creator grant; nested resources inherit rather than duplicating mutable ancestor ACLs. Store checks must cover search/catalog, export/import, history/restore, snapshots, annotation read/write/tag discovery, library connections and alert-rule folders. Existing entry points are `internal/server/dashboard_resources.go`, `internal/server/dashboard_history.go`, `internal/server/dashboard_history_resources.go`, `internal/server/dashboard_catalog.go`, `internal/server/dashboard_annotations.go`, `internal/server/annotations.go` and `internal/server/alerts.go`. Replace fabricated annotation user/login and history actor values with the trusted principal. Cross-organization resource lookup returns absence without disclosing another organization's metadata.

Membership/team/account removal spans identity and resource stores. Revoke the principal first, then remove its ACL assignments through a resumable cleanup operation before allowing membership recreation to inherit stale grants. Do not assume a foreign key can cascade between independent database files. Protect the last applicable administrator from accidental removal and define recovery through instance administration.

Frontend organization switching must clear or scope datasource-instance caches, query results, variable choices, pending queries and Live connections. `web/src/grafana/plugin-runtime.ts` currently resolves datasource instances in one workspace; module/package caches may be shared, but datasource instances need organization identity in their cache boundary. Refreshing a dashboard must continue to preserve same-context panel state, as verified by the TimeSeries regressions.

## Implementation sequence and acceptance

1. Establish the instance registry, organization server lifecycle and identity-free physical isolation first. Preserve organization 1 paths, data, raw JSON and credentials; prove duplicate UIDs in two organizations resolve independently. Do not expose multi-user administration before this boundary is complete.
2. Add principal resolution, sessions/Basic/service-account credentials, membership selection and SDK/backend context propagation. Reject foreign organization headers for service accounts and nonmembers. Bind Live credentials to principal, organization and revocation state; the existing cookie MAC contains only expiration (`internal/server/live.go:15`) and the hub sets every user ID to `1` (`internal/live/hub.go:120`).
3. Add central basic-role authorization and folder/dashboard/service-account ACL inheritance. Test every existing resource API, query/proxy route and background worker rather than relying on hidden UI buttons.
4. Add Windows PC administration UI and native CLI commands against the same APIs, including role changes, team membership, organization switching and token lifecycle. Preserve existing agent automation through a documented bootstrap/organization 1 migration credential.
5. Track remaining OSS authentication/integration behavior separately: password recovery/invites, supported OAuth/LDAP/auth-proxy/JWT modes, preferences, anonymous/public sharing policies, provisioning and the newer resource APIs. Completing steps 1–4 alone does not establish every OSS authentication feature.

Acceptance requires two organizations with identical dashboard/folder/library/datasource/target/rule/contact-point/annotation identities and distinct data/secrets; complete migration/restart verification of every table group above; ciphertext swap rejection; SQLite and ClickHouse separation; Viewer/Editor/Admin/None and server-admin matrices; direct/inherited ACL checks and moves; removal/revocation races; query/expression/resource/chunked/Live isolation; and PC/CLI workflows. Use the existing one-container integration fixture for external SQL and ClickHouse proof, with organization-specific app databases inside that fixture. This design introduces no additional Docker container requirement.
